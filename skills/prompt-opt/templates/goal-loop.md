# 循环任务(/goal /loop 指令)

## 适用信号

- 草稿明说要写给 Claude Code 原生 `/goal` 或 `/loop`(「帮我写个 goal」「来个 loop 盯着」),或语义是循环驱动:反复 / 定时 / 持续做 X、做到 Y 为止、盯着 / 监控 / 守着。
- 主交付物是一条可复制的 /goal 或 /loop 指令,不是本轮直接把任务做完(区别于修 bug / 加功能:那些一次做完)。
- 循环内核可以是任何场景(修测试、盯 CI、刷分数),按「是否循环驱动」判场景,不按内核。

## 字段骨架

- **目标**:循环要达成或维持什么,一句话;并选好形态——迭代到达标用 /goal,定时重复用 /loop(简单重复活用 /loop 就够,别硬上 /goal)。
- **上下文**:任务挂在哪个仓库 / 命令 / 流程上,验证要用到的环境(测试命令、CI 入口、评分工具)。
- **约束**:每轮允许动什么、不许动什么(如「只改实现,不许改测试断言来凑通过」);信息不足处标「假设:xxx」不虚构;测试命令 / PR 号 / 工具等环境可自查对象先自查再问。
- **验收标准**:即停止判据,必须确定性、可量化,独立评估者仅凭输出即可判真 / 假(测试 0 失败、退出码 0、分数 ≥ 阈值、清单清零);草稿只有主观说法(「更稳」「变好看」)时,改写为可量化判据并标假设,实在改不出就列澄清问题。
- **上限**:/goal 必带轮数上限(如「最多 5 轮」)控制开销;/loop 写明间隔(如 10m)与何时算完 / 何时取消。
- **每轮验证方式**:每轮跑什么命令、看什么数字、贴什么真实输出;有现成验证 skill / 脚本就指名,让循环能量化自查。

## 示例

**口语输入(→ /goal)**
> 帮我写个 goal:把这个项目测试修到全绿

**套骨架后的标准指令**
```
/goal 修复失败测试直到全部通过:测试命令退出码 0、0 failed(假设:测试命令先自查仓库确认,如 pytest / npm test);最多 5 轮。每轮:先跑测试贴真实失败清单 → 修复,只改实现不动测试断言(断言本身错了列出来待确认,不直接改);仍失败则带着新输出进下一轮;触顶仍未全绿则停下,汇报剩余失败清单与已试路径。
```

**口语输入(→ /loop)**
> 帮我盯着这个 PR 的 CI

**套骨架后的标准指令**
```
/loop 10m 检查当前分支 PR 的 CI 状态与新 review 评论(假设:PR 号先自查当前分支;间隔 10 分钟,可按 CI 时长调):CI 红 → 定位失败 job、修复并推送;有未回复评论 → 逐条处理并回复;全绿且无待办评论则本轮结束,等下一轮。整条循环的退出:PR 合并或关闭即停;同一失败连修 3 轮仍红,停下汇报而不是无限重试。
```
